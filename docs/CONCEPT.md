# Microshop

Microshop - легковесный headless-бэкенд интернет-магазина для частных продавцов с небольшим ассортиментом и ограниченным бюджетом. Система предназначена для быстрого запуска собственных онлайн-продаж без необходимости использовать крупные SaaS-платформы или разрабатывать полноценный интернет-магазин с нуля.

На первом этапе Microshop ориентирован только на российский рынок. Основная и единственная поддерживаемая валюта - российский рубль.

Одна установка Microshop обслуживает один магазин со своей базой данных, файлами, настройками и внешними подключениями. Мультитенантность и управление несколькими магазинами одной установкой не предусмотрены.

Backend предоставляет API и не зависит от конкретной витрины. Первый рабочий релиз поставляется со стандартной витриной и обязательным admin UI; стандартную витрину можно заменить собственным frontend или Telegram Mini App. Модель поставки описана в [DELIVERY.md](DELIVERY.md).

Основная бизнес-логика, включая расчет цен, скидок, доступности товаров и создание заказов, выполняется исключительно на сервере.

Таблицы, связи, ограничения и транзакционные правила описаны в [схеме данных](DATA_MODEL.md). Порядок проектирования и реализации зафиксирован в [плане](ROADMAP.md). Документы описывают целевое поведение: код приложения, миграции и поставка еще не реализованы.

## Основные требования

### Легковесность

Система должна быстро разворачиваться, потреблять умеренное количество ресурсов и не требовать сложной инфраструктуры для эксплуатации.

Предпочтительна простая архитектура с минимальным количеством внешних зависимостей.

### Полноценный базовый функционал

Несмотря на небольшой размер проекта, Microshop должен предоставлять все основные возможности, необходимые частному продавцу для начала торговли:

- каталог товаров;

- категории;

- варианты товаров;

- фотографии;

- учет наличия;

- изготовление на заказ;

- корзина;

- оформление заказов;

- управление заказами;

- способы оплаты;

- способы доставки;

- скидки и промокоды;

- уведомления;

- контактные данные покупателя в снимке заказа; отдельный каталог покупателей относится к v1.1;

- административный API;

- экспорт данных.


### Надежность

Торговые операции должны выполняться корректно даже при повторных запросах, параллельных покупках и ошибках клиента.

Система должна предотвращать:

- продажу отсутствующего товара;

- создание дублирующихся заказов;

- изменение цены со стороны клиента;

- использование недействительных скидок;

- просмотр чужих заказов;

- некорректное освобождение или списание остатков;

- несанкционированное изменение состояния заказа.

# Каталог

## Товары

Продавец может создавать товары со следующей основной информацией:

- название;

- slug;

- описание;

- фотографии;

- статус публикации;

- категории;

- порядок отображения.


Товар может находиться в одном из состояний:

- `DRAFT` - черновик;

- `ACTIVE` - опубликован и доступен на витрине;

- `HIDDEN` - временно скрыт;

- `ARCHIVED` - снят с продажи.


Товары, которые уже использовались в заказах, не должны физически удаляться таким образом, чтобы нарушалась история заказов.

В MVP товары архивируются; физическое удаление товаров через обычный API отсутствует.

## Категории

Товары можно объединять в категории.

Продавец самостоятельно:

- создает категории;

- задает их названия;

- изменяет порядок отображения;

- распределяет товары между категориями.


Категории предназначены только для организации каталога и не должны превращаться в сложную иерархическую CMS.

---

# Варианты товаров

Один товар может иметь несколько вариантов.

Например:

```
Футболка
├── Black / S
├── Black / M
├── Black / L
└── White / M
```

Каждый вариант может иметь собственные:

- характеристики;

- цену;

- фотографии;

- артикул;

- режим наличия;

- остаток.


Характеристики варианта можно хранить как простой набор пар ключ-значение:

```
Размер: M
Цвет: Black
```

Создание сложной универсальной системы атрибутов на первом этапе не требуется.

В первой версии любой товар имеет хотя бы один вариант, включая базовый вариант без пользовательских характеристик. Фотографии образуют общую галерею товара; отдельные фотографии могут быть привязаны к варианту. При его выборе сначала показываются собственные фотографии варианта, затем общие, затем фотографии остальных вариантов. Независимые копии галерей не создаются.

---

# Цены

Цена определяется вариантом товара.

Если товар не имеет пользовательских вариантов, он создается с одним базовым вариантом без характеристик.

Все цены задаются в российских рублях.

Денежные значения внутри системы должны храниться в минимальных денежных единицах - копейках.

Например:

```
125050 = 1250.50 ₽
```

Использование floating-point типов для хранения денежных значений не допускается.

Нулевые цены и нулевой итог заказа допустимы. Если итог равен нулю, оплата не требуется: заказ автоматически получает `PAID` с отметкой отсутствия денежного платежа. Срок ожидания оплаты не назначается; регистрировать денежный возврат для такого заказа нельзя.

При оформлении заказа клиент никогда не передает итоговую цену как доверенное значение.

Backend самостоятельно рассчитывает:

```
стоимость товаров
скидку
стоимость доставки
итоговую сумму
```

---

# Наличие товаров

Для каждого варианта задается способ продажи.

Основные режимы:

```
IN_STOCK
MADE_TO_ORDER
UNAVAILABLE
```

## IN_STOCK

Товар существует физически и имеет ограниченный остаток.

Например:

```
stockQuantity = 5
```

Покупатель не может оформить количество товара, превышающее доступный остаток.

## MADE_TO_ORDER

Товар производится после оформления заказа.

Для него могут задаваться:

```
productionTimeDays
acceptingOrders
```

В дальнейшем может быть добавлено ограничение одновременно принятых заказов:

```
maxActiveOrders
```

Это позволяет продавцу временно прекращать прием заказов, если производственная нагрузка становится слишком большой.

## UNAVAILABLE

Товар временно нельзя заказать, но он может оставаться видимым в каталоге.

# Резервирование товаров

Одной проверки остатка перед созданием заказа недостаточно.

Например, если осталась одна единица товара, два покупателя могут одновременно увидеть ее доступной и попытаться оформить заказ.

Поэтому создание заказа должно атомарно резервировать необходимое количество товара.

Условно:

```
stock = 5
reserved = 2
available = 3
```

При отмене заказа соответствующий резерв освобождается.

До передачи товара покупателю или перевозчику зарезервированные единицы остаются в складском остатке, но недоступны для новых заказов. Окончательное списание выполняется при отправке заказа, а при самовывозе — при выдаче покупателю. Списание остатка и закрытие резерва выполняются атомарно и не повторяются при повторном запросе.

Отмена освобождает только активный резерв. Уже списанные единицы не возвращаются в остаток автоматически; регистрация возврата денег также не означает возврат товара на склад.

Для способа оплаты с требованием предоплаты продавец может задать срок ожидания оплаты:

```
paymentDeadline
```

Если срок задан, активный неоплаченный заказ после его истечения автоматически отменяется, а активные резервы освобождаются. Проверка и отмена выполняются под блокировкой заказа, общей с подтверждением оплаты. Без настроенного срока автоматическая отмена по времени не выполняется. У заказа с нулевым итогом срок оплаты отсутствует.

# Корзина

Покупатель может использовать магазин без регистрации.

Для корзины создается случайный идентификатор или token.

Корзина позволяет:

- добавить вариант товара;

- удалить вариант;

- изменить количество;

- применить промокод;

- получить актуальный расчет стоимости;

- выбрать способ доставки;

- очистить корзину.


Клиент передает только необходимые данные:

```
variantId
quantity
promoCode
deliveryMethodId
```

Backend самостоятельно определяет цены.

Для расчета промокода с персональным лимитом запрос может дополнительно
содержать телефон или email, выбранный у промокода. Контакт используется только
в этом расчете и не сохраняется в корзине. Без нужного контакта скидка не
учитывается, а результат содержит причину `NEED_CONTACT`. После ввода контакта
корзина пересчитывается. Предварительный расчет не занимает лимит; checkout
повторно проверяет контакт и лимит в своей транзакции.

Пример результата расчета:

```
itemsSubtotal: 5000 ₽
discount: -500 ₽
delivery: 300 ₽
total: 4800 ₽
```

# Checkout

Checkout отвечает непосредственно за преобразование корзины в заказ.

Покупатель может передать:

- имя;

- телефон;

- email;

- Telegram или другой контакт;

- адрес доставки;

- способ получения;

- способ оплаты;

- комментарий.


Набор обязательных контактов определяется настройками магазина.

Например, небольшому продавцу, работающему через Telegram, может быть достаточно имени и телефона или Telegram.

Типичный процесс оформления:

```
валидация корзины
↓
пересчет цен
↓
проверка промокода
↓
проверка наличия
↓
резервирование товаров
↓
создание заказа
↓
закрытие корзины и запись истории и уведомлений
↓
commit торговой транзакции
↓
внешняя отправка сохраненных уведомлений
```

Создание заказа, снимков, резервов, использования промокода, закрытие корзины, запись успешного checkout, истории и уведомлений выполняются одной транзакцией. Внешняя отправка уведомлений происходит после commit; ее сбой не откатывает заказ.

---

# Идемпотентность оформления заказа

Повторный запрос от клиента не должен создавать второй заказ.

Например, пользователь нажал кнопку оформления, запрос выполнился на сервере, но клиент получил timeout и автоматически повторил его.

Для защиты от этого checkout должен поддерживать механизм идемпотентности.

Например:

```
Idempotency-Key
```

Повторный запрос с тем же ключом должен вернуть результат первоначальной операции вместо создания нового заказа.

---

# Заказы

Заказ является центральной сущностью торговой части Microshop.

Он содержит:

- номер;

- дату создания;

- данные покупателя;

- позиции;

- цены;

- примененные скидки;

- способ оплаты;

- способ доставки;

- стоимость доставки;

- итоговую сумму;

- комментарий;

- состояния оплаты и выполнения.


## Snapshot данных

Позиция заказа не должна зависеть от текущего состояния товара в каталоге.

При создании заказа сохраняется snapshot данных.

Например:

```
productId
variantId

productName
variantName
attributes
imageUrl

unitPrice
quantity
discount
total
```

Если продавец после оформления заказа изменит:

```
Чехол для iPhone
1500 ₽
```

на:

```
Чехол Premium
2500 ₽
```

старый заказ должен продолжать отображать исходное название и цену 1500 ₽.

То же правило относится к данным доставки, оплаты и покупателя.

---

# Состояния заказа

Не следует объединять все состояния в один большой `OrderStatus`.

Состояние самого заказа, оплаты и выполнения учитываются отдельно.

## OrderStatus

```
ACTIVE
COMPLETED
CANCELLED
```

## PaymentStatus

```
PENDING
PAID
PARTIALLY_REFUNDED
REFUNDED
```

## FulfillmentStatus

```
PENDING
PROCESSING
READY
SHIPPED
DELIVERED
```

Такой подход предотвращает появление большого количества комбинированных состояний вида:

```
PAID_BUT_NOT_SHIPPED
PAID_AND_SHIPPED
REFUNDED_AFTER_DELIVERY
```

---

## Правила переходов

Выполнение движется вперед: `PENDING → PROCESSING → READY → SHIPPED → DELIVERED`. Промежуточные этапы обработки и готовности можно пропустить; при доставке отправка обязательно фиксируется перед получением. Для самовывоза выдача переводит заказ непосредственно в `DELIVERED`, без `SHIPPED`.

Способ оплаты определяет необходимость предоплаты. Ручная предоплата требует подтверждения до передачи товара; оплата при самовывозе — при выдаче. Для `OTHER` продавец явно задает необходимость предоплаты. При полном денежном возврате до передачи предоплаченного заказа передача запрещена. Подтверждение оплаты и выдачу при самовывозе можно выполнить одной операцией.

Завершение разрешено для активного доставленного заказа после выполнения обязательства по оплате, включая нулевой итог. Отмена разрешена для активного заказа, в том числе после отправки, но уже списанные товары автоматически на склад не возвращаются. Завершенный или отмененный заказ не открывается повторно. Денежный возврат учитывается отдельно и не меняет автоматически состояния заказа и выполнения. Факт получения ранее отправленного отмененного заказа можно зарегистрировать, сохранив `CANCELLED`.

Повтор уже выполненного перехода не создает новое событие и не повторяет списание или освобождение резерва. Обратный или запрещенный переход отклоняется. Частичная отправка, изменение состава оформленного заказа и отмена отдельных позиций в первой версии не поддерживаются.

# История заказа

Все существенные изменения состояния заказа должны попадать в историю.

Для этого используется лог событий заказа.

Примеры:

```
ORDER_CREATED
PAYMENT_MARKED_PAID
FULFILLMENT_STARTED
ORDER_READY
ORDER_SHIPPED
ORDER_COMPLETED
ORDER_CANCELLED
REFUND_REGISTERED
COMMENT_ADDED
```

История позволяет отображать покупателю и продавцу последовательность обработки:

```
12:41 Заказ создан
13:15 Оплата подтверждена
15:32 Заказ передан в обработку
18:20 Заказ отправлен
```

Она также помогает разбирать спорные ситуации.

# Оплата

На первом этапе Microshop не выполняет автоматическую обработку денежных платежей.

Продавец самостоятельно принимает оплату и подтверждает ее в административном интерфейсе.

Учитывается одно подтверждение полной оплаты заказа; частичные входящие платежи в первой версии не поддерживаются. Для нулевого итога система сохраняет отдельную отметку `ZERO_TOTAL`, которая закрывает обязательство по оплате, но не означает поступление денег. Новый ручной платеж для отмененного заказа не регистрируется.

Продавец может настроить несколько способов оплаты.

Например:

```
Перевод по СБП

Переведите сумму заказа по номеру:
+7 ...

После оплаты продавец подтвердит получение средств.
```

Базовые типы:

```
MANUAL_PREPAYMENT
CASH_ON_PICKUP
OTHER
```

В дальнейшем могут быть добавлены интеграции:

```
YOOKASSA
TINKOFF
CLOUDPAYMENTS
```

Платежные интеграции должны добавляться как адаптеры, не меняя основную модель заказа.

---

# Возвраты

На первом этапе фактический возврат денег выполняется продавцом вручную.

После выполнения возврата продавец регистрирует его в Microshop.

Система должна поддерживать:

```
PAID
PARTIALLY_REFUNDED
REFUNDED
```

Фактическая сумма возврата также должна сохраняться.

---

# Доставка

Продавец может создавать собственные способы получения заказа.

Для каждого способа задаются:

- название;

- тип;

- описание;

- стоимость;

- доступность.


Основные типы:

```
PICKUP
FIXED_PRICE
FREE
CUSTOM
```

Например:

```
Самовывоз
0 ₽

СДЭК
350 ₽

Почта России
400 ₽
```

В первой версии Microshop не рассчитывает тарифы транспортных компаний; используются цены, заданные продавцом.

Для `CUSTOM` продавец задает собственный способ получения с заранее известной неотрицательной ценой. Согласование стоимости доставки и изменение итоговой суммы после создания заказа не входят в первую версию. Для `PICKUP` и `FREE` цена равна нулю. Необходимость адреса задается независимо от цены; оплата `CASH_ON_PICKUP` доступна только при самовывозе.

После создания заказа информация о доставке сохраняется snapshot'ом:

```
deliveryMethodName
deliveryPrice
deliveryAddress
trackingNumber
```

Продавец может добавить номер отслеживания после отправки заказа.

В дальнейшем могут появиться интеграции со СДЭК и другими службами доставки.

---

# Доступ покупателя к заказу

Регистрация покупателя не требуется.

После создания заказа система генерирует криптографически случайный access token.

Например:

```
/order/3b72fc...
```

Token дает доступ только к конкретному заказу.

Последовательные идентификаторы не должны использоваться как средство авторизации:

```
/orders/125
```

может существовать как внутренний URL административного API, но не как публичная ссылка покупателя.

Дополнительно заказ получает удобный человеческий номер:

```
MS-000142
```

Он может использоваться продавцом и покупателем при общении, но не является credential для доступа к заказу.

# Покупатели

В MVP регистрация покупателя отсутствует. Контакты хранятся в снимке заказа;
отдельной сущности `Customer`, каталога покупателей и автоматического объединения
заказов по контактам нет. Персональный лимит промокода использует нормализованный
контакт, но не создает аккаунт или CRM-запись.

Каталог покупателей и история покупателя относятся к v1.1. Правила связывания
заказов и объединения контактов проектируются в рамках этой версии. Изменение
будущей записи покупателя не должно менять снимки старых заказов или предоставлять
доступ к другим заказам.

# Скидки товара

Простые скидки непосредственно на товар или вариант можно задавать через две цены:

```
price = 2500
compareAtPrice = 3000
```

На витрине это отображается примерно как:

```
3000 ₽ → 2500 ₽
```

Такая скидка считается частью текущей цены товара и не является промокодом.

# Промокоды

Промокоды являются отдельным механизмом скидок.

Основные типы:

```
PERCENT
FIXED
```

Для промокода могут задаваться:

```
startsAt
endsAt

minimumOrderAmount

maxUses
maxUsesPerCustomer

applicableProducts
applicableCategories

enabled
```

Backend проверяет применимость промокода при каждом пересчете корзины и повторно при checkout.

Использование промокода учитывается при создании заказа. Проверка лимитов и регистрация использования выполняются атомарно с созданием заказа. При отмене неоплаченного заказа использование освобождается. После подтвержденной положительной оплаты отмена или возврат денег не восстанавливают лимит использования.

Для персонального лимита продавец выбирает у промокода идентификатор покупателя: телефон или email. Применение такого промокода требует выбранного контакта; лимит учитывается по его нормализованному значению. Это ограничение по заявленному контакту без подтверждения личности: ввод другого контакта может обойти лимит. Аккаунт покупателя для этого не создается.

Минимальная сумма для применения промокода считается по стоимости всех товаров корзины до скидки промокода, без доставки. Скидка рассчитывается по текущим ценам только для подходящих позиций: явно указанных товаров или товаров из указанных неархивных категорий. Если ограничения по товарам и категориям отсутствуют, подходят все товары. Фиксированная скидка не превышает стоимость подходящих позиций; доставка не дисконтируется.

Процент задается с точностью до сотой доли процента; скидка округляется вниз до копейки. Общая скидка распределяется по позициям с сохранением точной суммы, по правилам схемы данных. Промокод без подходящих позиций или с нулевой рассчитанной скидкой не применяется; при checkout выбранный недействительный промокод вызывает ошибку валидации.

Отмена заказа с нулевым итогом освобождает использование промокода: автоматическая отметка `ZERO_TOTAL` не является фактической оплатой. Для положительного подтвержденного платежа использование не освобождается даже после полного возврата.

Первый релиз не должен поддерживать сложные promotion-механики вроде:

- buy 2 get 1;

- комбинации множества условий;

- stacking нескольких промокодов;

- персональные прайс-листы;

- сложные программы лояльности.

# Уведомления

Система должна поддерживать уведомления продавца и покупателя.

## Уведомления продавца

В MVP канал уведомлений продавца — Telegram. Владелец задает bot token и chat id
в настройках уведомлений и может отключить канал.

Например:

```
Новый заказ #MS-142

3 товара
4 850 ₽

Оплата: СБП
Доставка: СДЭК
```

Продавец получает уведомления о создании и отмене заказа, включая
автоматическую отмену. Другие события не создают уведомлений продавцу в MVP.

## Уведомления покупателя

В MVP канал уведомлений покупателя — email через настроенный SMTP-сервер.
Канал можно отключить. Если email покупателя отсутствует, уведомление не
создается; наличие email не становится обязательным условием покупки только
ради уведомлений.

Основные события:

```
ORDER_CREATED
PAYMENT_MARKED_PAID
ORDER_SHIPPED
ORDER_CANCELLED
```

Механизм уведомлений не должен быть жестко связан с конкретным SMTP-сервисом или Telegram API.

Конкретные каналы доставки должны подключаться через отдельные реализации.

Заказ с нулевым итогом получает уведомление о создании с указанием, что оплата
не требуется; отдельное уведомление о поступлении денег не создается.
Готовность к самовывозу, доставка, завершение и денежный возврат не создают
уведомлений покупателю в MVP.

### Отправка и ошибки

Записи уведомлений создаются в торговой транзакции и отправляются после commit.
Повтор торговой операции не создает новое уведомление о том же событии.
Гарантия доставки ровно один раз внешнему получателю отсутствует: после
успешной внешней отправки и сбоя записи результата возможно повторное сообщение.

Всего выполняется не более пяти попыток: первая сразу после commit, повторы
через 1, 5, 30 и 120 минут после предыдущей временной ошибки. Сетевая
недоступность, timeout, ограничение частоты и временная ошибка сервиса допускают
повтор; явная постоянная ошибка адресата, авторизации или конфигурации сразу
переводит уведомление в `FAILED`. Требуемая сервисом задержка при ограничении
частоты может увеличить интервал, но не число попыток. `FAILED` после постоянной
ошибки или исчерпания попыток доступен владельцу в admin UI. Уведомления
в `FAILED` не участвуют в автоматической отправке.

Формат настроек каналов, захват очереди и учет попыток описаны в DATA_MODEL.md.

# Управление магазином

Административный API должен позволять владельцу магазина полностью управлять торговыми операциями.

Первый рабочий релиз включает отдельный admin UI, который использует административный API. Реализация начинается с backend; готовность API сама по себе не означает готовность полного релиза.

## Dashboard

Минимальная статистика:

- новые заказы;

- неоплаченные заказы;

- заказы, ожидающие отправки;

- количество заказов за сегодня;

- выручка.


Выручка за период — сумма положительных подтвержденных оплат с `confirmed_at`
в периоде минус сумма денежных возвратов с `registered_at` в периоде. Дата
создания заказа не определяет попадание денежной операции в период. Оплата
отмененного заказа учитывается до регистрации фактического возврата.
`ZERO_TOTAL` не является поступлением денег. Результат за период может быть
отрицательным, если возвраты превышают поступления за тот же период.

Начальная и конечная даты включены в выбранный календарный период магазина:
для запроса БД они преобразуются в интервал от начала первой даты до начала
дня после последней даты, с исключенной верхней границей. Используется часовой
пояс магазина, а не браузера или сервера. «За сегодня» означает текущую
календарную дату магазина; количество заказов считается по `created_at`.

# Публикация магазина

До публикации публичная работа магазина недоступна. Для публикации требуются:

- завершенное создание владельца;
- непустое название магазина;
- хотя бы один заполненный контакт продавца;
- непустые условия продажи;
- правила контактов покупателя, соответствующие схеме DATA_MODEL.md;
- хотя бы одна совместимая пара включенных и неархивных способов оплаты
  и получения заказа.

Пустой каталог допустим: наличие опубликованного или доступного товара не
является условием публикации. Описание, логотип, цвета и включение уведомлений
необязательны. Настройка оформления витрины ограничена названием, описанием,
контактами, логотипом, основным цветом и цветом фона; ее хранение описано в
DATA_MODEL.md, поставка интерфейсов — в DELIVERY.md.

Публикация открывает каталог. Разрешение приема заказов учитывается отдельно
через `sales_enabled`; новый checkout проверяет публикацию, разрешение продаж
и актуальную готовность торговых настроек. Эти проверки не блокируют повтор
уже успешного checkout с исходным ключом идемпотентности.

# Основные домены

Области MVP; это перечень ответственности, а не структура пакетов приложения:

```
Shop

Catalog
├── Product
├── ProductVariant
├── ProductImage
└── Category

Cart
├── Cart
└── CartItem

Ordering
├── Order
├── OrderItem
└── OrderEvent

Payments
├── PaymentMethod
├── OrderPayment
└── OrderRefund

Delivery
└── DeliveryMethod

Promotions
└── PromoCode

Notifications
└── Notification
```

Microshop должен оставаться компактным backend'ом, который предоставляет небольшой продавцу действительно необходимые инструменты для торговли, но не пытается воспроизвести Shopify, Magento или полноценную ERP.

Основной технический приоритет системы - корректность торговых операций: checkout, расчет цены, резервирование остатков, жизненный цикл заказа, оплата, отмена и возврат. Область Customers добавляется в v1.1; она не входит в MVP.
