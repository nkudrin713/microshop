# Microshop: поставка, frontend и deployment

## Общий подход

Microshop остается **headless по архитектуре**, но поставляется как готовый продукт.

Пользователь после установки получает:

- backend;
- стандартную витрину;
- admin UI;
- PostgreSQL;
- reverse proxy;
- HTTPS после подключения домена.

Разработчик управляет версиями продукта и выпускает готовые образы backend и web в GHCR. Пользователь получает только deployment-комплект, настраивает окружение и запускает управляющие скрипты. Сборка приложения на сервере пользователя не требуется.

Стандартный frontend не является частью бизнес-логики backend и при необходимости может быть заменен пользовательским frontend-приложением.

Главный принцип:

> Headless по архитектуре, batteries included по поставке.

---

# Архитектура

Базовая production-схема:

```text
Internet
   │
   ▼
 Caddy
 ├── /          → Storefront
 ├── /admin     → Admin UI
 └── /api/*     → Spring Boot
                     │
                     ▼
                 PostgreSQL
```

Backend реализуется на Kotlin + Spring Boot. Доступ к PostgreSQL — Spring Data JPA с Hibernate; явные запросы задаются на методах репозиториев через `@Query` (JPQL или native SQL). Правила торговых транзакций и блокировок определены в [DATA_MODEL.md](DATA_MODEL.md) и сохраняются при использовании JPA.

Frontend считается недоверенным клиентом. Все критические торговые операции выполняются и проверяются на backend:

- расчет цен;
- проверка наличия;
- резервирование товара;
- расчет скидок;
- checkout;
- создание заказа;
- изменение состояния заказа;
- работа с оплатой;
- доставка.

---

# Frontend

Microshop поставляет два frontend-приложения.

Единый стек admin UI и стандартной витрины — Vue 3, TypeScript и Vite.
Оба приложения собираются в статические файлы; отдельный frontend-сервер
и серверный рендеринг в MVP отсутствуют. Торговые данные загружаются из API
во время работы интерфейса, без пересборки при изменении каталога или настроек.

## Storefront

Публичная витрина магазина.

Основные страницы:

```text
/
каталог
категории
товар
корзина
checkout
просмотр заказа
```

Storefront поставляется по умолчанию, чтобы установленный Microshop сразу был полноценным интернет-магазином.

При этом storefront является отдельным клиентом публичного API и может быть:

- отключен;
- заменен;
- переписан;
- размещен отдельно.

Разработчик может использовать Microshop только как headless backend и подключить собственный frontend.

Например:

```text
React
Vue
Svelte
Astro
Next.js
Telegram Mini App
native application
```

## Admin UI

Административный интерфейс магазина.

Он поставляется обязательно.

Пример URL:

```text
/admin
```

Через него продавец управляет:

- товарами;
- категориями;
- вариантами;
- остатками;
- заказами;
- оплатами;
- возвратами;
- доставкой;
- промокодами;
- настройками;
- уведомлениями.

---

# Разделение backend и frontend

Frontend не должен быть встроен в Spring Boot как основная часть приложения.

Исходный код проекта логически разделяется:

```text
microshop/
├── backend/
├── frontend/
│   ├── storefront/
│   └── admin/
└── deploy/
```

Backend предоставляет API:

```text
/api/storefront/...
/api/admin/...
```

Storefront и Admin UI используют эти API как обычные клиенты.

Такое разделение позволяет изменять frontend независимо от бизнес-логики backend.

---

# Поставка frontend

Frontend собирается заранее в CI.

Production-сборка storefront и admin представляет собой статические файлы.

Их можно включить непосредственно в Docker image с Caddy.

В результате production deployment состоит из трех контейнеров:

```text
microshop-web
├── Caddy
├── Storefront
└── Admin UI

microshop-backend
└── Spring Boot

postgres
└── PostgreSQL
```

Caddy выполняет сразу несколько задач:

- принимает HTTP/HTTPS;
- автоматически управляет TLS;
- отдает storefront;
- отдает admin UI;
- проксирует `/api/*` в Spring Boot.

Frontend не требуется отдавать через Spring Boot.

---

# URL-схема

Базовая схема:

```text
/                       storefront
/catalog
/product/{slug}
/cart
/checkout
/order/{token}

/admin                   admin UI
/admin/products
/admin/orders
/admin/settings

/api/storefront/...      public API
/api/admin/...           authenticated API
```

Storefront, admin UI и backend работают через один hostname.

Это позволяет избежать необходимости настраивать CORS для стандартной поставки.

# Кастомизация storefront

Стандартный storefront должен быть универсальным, но не превращаться в конструктор сайтов.

В первом рабочем релизе поддерживаются только следующие настройки:

```text
logo
store name
store description

primary color
background color

contacts
```

Шрифт и компоновка фиксированы стандартной витриной. Выбор шрифта,
hero-изображение, отдельный список социальных ссылок, переключатели отображения
недоступных товаров, категорий, количества остатка и срока изготовления
в MVP отсутствуют. Полноценный page builder в scope проекта не входит.

Название, описание и контакты используют существующие поля `shop_settings`.
Логотип хранится через `logo_file_id`, цвета — через `primary_color` и
`background_color` в той же таблице. Формат и ограничения определены в
DATA_MODEL.md. Настройки загружаются через API; изменение названия, оформления
или контактов не требует пересборки frontend. Отсутствие логотипа и выбранных
цветов означает использование стандартного оформления поставляемой витрины.

```text
1–2 GB RAM
```

- Java;
- Gradle;
- Node.js;
- PostgreSQL;
- Caddy;
- nginx;
- certbot.

Все необходимые компоненты поставляются как Docker images.

# Установка

Каждый релиз включает deployment-архив, публикуемый в GitHub Release вместе со ссылками на готовые образы в GHCR:

```text
microshop-deploy-1.4.0.tar.gz
├── compose.yaml
├── .env.example
├── install.sh
├── update.sh
├── domain.sh
├── backup.sh
└── restore.sh
```

Compose и скрипты относятся к той же версии Microshop, что backend и frontend. Исходники приложения и Git на сервере пользователя не требуются.

Пользователь скачивает архив опубликованного стабильного релиза. После скачивания основной сценарий:

```bash
mkdir microshop
tar -xzf microshop-deploy-1.4.0.tar.gz -C microshop
cd microshop
./install.sh
```

`install.sh` отвечает только за инфраструктуру.

Он должен:

```text
проверить окружение
↓
создать .env
↓
сгенерировать secrets
↓
скачать Docker images
↓
запустить Docker Compose
↓
дождаться healthcheck
↓
показать адрес магазина и одноразовый setup-token
```

Пользователь не должен собирать приложение на своем сервере.

---

# Проверка окружения

Installer проверяет наличие:

```text
Linux
Docker Engine
Docker Compose
curl
tar
```

Installer проверяет доступ к работающему Docker Engine, поддерживаемые версии Docker и Compose, архитектуру сервера, свободное место и доступность необходимых портов.

В первой версии installer не устанавливает Docker и не меняет настройки операционной системы. При отсутствии необходимого окружения он сообщает, что нужно установить, и завершает работу.

# Конфигурация

При первом запуске installer создает `.env` из шаблона:

```text
.env.example
↓
.env
```

Secrets генерируются автоматически.

Например:

```text
POSTGRES_PASSWORD
APP_SECRET
ORDER_TOKEN_SECRET
SETUP_TOKEN
```

Пример:

```dotenv
POSTGRES_DB=microshop
POSTGRES_USER=microshop
POSTGRES_PASSWORD=<generated>

APP_SECRET=<generated>
ORDER_TOKEN_SECRET=<generated>
SETUP_TOKEN=<generated>

DOMAIN=
```

`.env` не хранится в Git.

Файл доступен только владельцу установки. Повторный запуск installer сохраняет существующие secrets, конфигурацию и данные. Отсутствующие обязательные параметры существующей установки требуют явного исправления, а не автоматической замены secrets.

Версия продукта и ссылки на образы определяются deployment-комплектом, а не выбираются отдельно пользователем. Обновление не заменяет пользовательскую `.env`; изменения ее формата применяются с сохранением существующих значений.

Пользователь не должен самостоятельно придумывать внутренние технические secrets.

# Сборка и CI

Microshop не собирается на VPS пользователя.

Сборкой занимается CI проекта.

В качестве CI используется GitHub Actions.

Базовый release pipeline:

```text
push tag v1.0.0
      ↓
tests
      ↓
build backend
      ↓
build storefront
      ↓
build admin
      ↓
build Docker images
      ↓
push backend and web images to GHCR
      ↓
create deployment archive with image digests
      ↓
publish GitHub Release
```

В качестве registry используется GitHub Container Registry. Образы публичные, чтобы пользователь мог скачивать их без GitHub-аккаунта и registry credentials.

Например:

```text
ghcr.io/<owner>/microshop-backend:1.0.0
ghcr.io/<owner>/microshop-web:1.0.0
```

Теги опубликованных версий не перезаписываются. Compose фиксирует образы по digest, чтобы повторная установка релиза использовала те же образы.

Релиз становится доступен для установки и обновления только после успешной публикации обоих образов и deployment-архива. Наличие Git-тега или отдельного образа не означает готовность релиза.

Управляющие скрипты на сервере пользователя скачивают готовые образы и запускают их через Compose:

```bash
docker compose pull
docker compose up -d
```

Пользователю не нужны:

```text
JDK
Gradle
Node.js
npm
```

# Версионирование

Backend, storefront и admin считаются частями одного релиза Microshop.

Например:

```text
Microshop 1.4.0

backend    1.4.0
storefront 1.4.0
admin      1.4.0
deployment 1.4.0
```

Пользователь не должен самостоятельно выбирать совместимые версии компонентов.

Обновляется продукт целиком.

Для каждого релиза разработчик определяет поддерживаемые исходные версии. Если необходим промежуточный релиз, `update.sh` сообщает об этом и не выполняет неподдерживаемый переход.

Версия PostgreSQL выбирается разработчиком и фиксируется в Compose отдельно от версии Microshop. Обновление major-версии PostgreSQL требует отдельной процедуры переноса данных и не выполняется обычной заменой образа в `update.sh`.

# Docker Compose

Базовый production stack:

```text
Docker Compose

├── web
├── backend
└── postgres
```

Не требуется добавлять без необходимости:

```text
Redis
Kafka
RabbitMQ
MinIO
Elasticsearch
Kubernetes
```

Microshop должен оставаться простым single-instance приложением.

Persistent storage используется для PostgreSQL, пользовательских файлов и данных Caddy с сертификатами и ключами. Пересоздание контейнеров при обновлении сохраняет эти данные.

---

# Миграции БД

SQL-миграции выполняет Flyway при старте backend. `install.sh` не запускает
миграции отдельно. Hibernate только проверяет соответствие сущностей схеме
(`ddl-auto=validate`) и не создает или изменяет таблицы.

```text
Spring Boot starts
      ↓
connect PostgreSQL
      ↓
Flyway migrate
      ↓
application starts
```

Если миграция не прошла, приложение не должно считаться успешно запущенным.

---

# Healthcheck

Installer должен проверять не только успешный запуск Docker Compose, но и реальную готовность приложения.

Backend предоставляет endpoint готовности:

```text
/actuator/health
```

Установка считается завершенной только после успешной проверки.

Проверка готовности backend учитывает завершение миграций и доступность БД. Отдельно проверяются storefront и API через web. У каждой проверки есть timeout; при ошибке скрипт завершает работу с ненулевым кодом и показывает диагностику.

Готовность инфраструктуры не зависит от завершения setup wizard: приложение должно успешно пройти healthcheck и в состоянии `UNINITIALIZED`.

Пример вывода:

```text
Waiting for Microshop...

Database connected ✓
Application started ✓
Web server available ✓

Microshop is running.
```

# Первый запуск

`install.sh` не должен превращаться в интерактивную анкету по настройке магазина.

Через терминал не следует спрашивать:

```text
название магазина
описание
контакты
email
пароль администратора
Telegram
оплату
доставку
```

После запуска инфраструктуры пользователь открывает Microshop через защищенное соединение и проходит setup wizard.

Первоначальное состояние:

```text
UNINITIALIZED
```

Пока приложение находится в этом состоянии, обычная работа магазина недоступна.

Installer генерирует одноразовый setup-token и показывает его владельцу установки. Backend требует этот token для создания первого владельца; открытого создания первого аккаунта без token нет.

Создание владельца, использование token и переход состояния выполняются атомарно. Одновременные запросы не могут создать нескольких владельцев.

Первый этап setup wizard:

```text
проверка setup-token
↓
создание владельца
↓
блокировка повторного создания владельца
```

Сразу после создания владельца:

```text
INITIALIZED
```

Повторное создание владельца через setup становится невозможным.

Первый пользователь получает роль владельца магазина.

Название магазина, контакты, оплату и доставку владелец настраивает после входа в admin UI. Настройку можно продолжить позже; она не открывает повторно создание владельца. Публикация выполняется по правилам раздела «Публикация магазина» в [CONCEPT.md](CONCEPT.md): каталог может быть пустым, уведомления и оформление необязательны. Прием заказов управляется отдельно через `sales_enabled`.

Сложная ролевая модель для первой версии не требуется.

# Работа без домена

Домен не должен быть обязательным для первоначального запуска.

После установки Microshop может быть доступен по IP:

```text
http://185.123.45.67
```

Это позволяет сначала проверить работу магазина, а домен подключить позже.

HTTP по публичному IP используется только для предварительной проверки без передачи паролей и setup-token. Создание владельца и вход в admin UI выполняются через HTTPS после подключения домена либо через SSH-туннель до его подключения. Публичный HTTP-доступ к setup и admin API в этом режиме закрыт.

---

# Подключение домена

DNS остается ответственностью владельца домена.

Например, IP VPS:

```text
185.123.45.67
```

Для поддомена пользователь создает DNS-запись:

```text
Type: A
Name: shop
Value: 185.123.45.67
```

Для корневого домена:

```text
Type: A
Name: @
Value: 185.123.45.67
```

После изменения DNS пользователь выполняет:

```bash
./domain.sh shop.example.ru
```

---

# domain.sh

Скрипт подключения домена должен:

```text
проверить hostname и диагностировать DNS A/AAAA
↓
записать DOMAIN в конфигурацию
↓
пересоздать web с новым environment
↓
проверить HTTPS для заданного hostname
```

После этого магазин доступен по адресу:

```text
https://shop.example.ru
```

Caddy самостоятельно получает и продлевает TLS-сертификат.

В стандартной поставке `DOMAIN` передается в web через Compose. Изменение `.env` не меняет environment существующего контейнера, поэтому одного reload Caddy или `docker compose restart` недостаточно. Скрипт применяет конфигурацию через `docker compose up -d web`, сохраняя persistent storage Caddy.

DNS-проверка учитывает A и AAAA, задержку распространения записей и показывает диагностические сообщения. Итоговая проверка имеет timeout и подтверждает доступность HTTPS с действительным сертификатом именно для указанного hostname. Запуск контейнера сам по себе не означает успешное подключение домена.

Для работы автоматического HTTPS порты 80 и 443 должны быть доступны извне.

# Автоматизация DNS

Microshop не должен требовать доступа к аккаунту регистратора или DNS-провайдера.

В базовой версии пользователь самостоятельно создает DNS-запись.

Интеграции с DNS-провайдерами не входят в первую версию.

# Обновление

Пользователь обновляет магазин одной командой:

```bash
./update.sh
```

Типичный процесс:

```text
определение опубликованного стабильного релиза и допустимости перехода
↓
скачивание deployment-комплекта и всех целевых образов
↓
проверка конфигурации и свободного места
↓
остановка backend с завершением текущих операций
↓
создание согласованного backup
↓
применение нового deployment-комплекта с сохранением .env и данных
↓
запуск новой версии и миграции БД при старте backend
↓
healthcheck backend и проверка через web
↓
фиксация успешного обновления
```

Скачивание выполняется до остановки магазина. Для первой версии допустима короткая остановка на время backup, миграций и запуска; обновление без простоя не требуется.

Скрипт обновляет Compose и управляющие скрипты вместе с образами продукта. Текущий deployment-комплект сохраняется до успешного завершения обновления. Параллельный запуск update, backup и restore не допускается.

При ошибке до остановки backend магазин продолжает работать на текущей версии. При ошибке после остановки скрипт не сообщает об успехе, сохраняет диагностику, предыдущий deployment-комплект и созданный backup.

Возврат старых образов после миграций БД не гарантирует восстановление работоспособности. Автоматическое восстановление данных не выполняется: `restore.sh` запускается явно, поскольку восстановление может удалить изменения, появившиеся после backup.

Пример:

```text
Microshop 1.3.2 → 1.4.0

Downloading update... ✓
Checking configuration... ✓
Stopping Microshop... ✓
Creating backup... ✓
Starting Microshop and applying migrations... ✓
Checking health... ✓

Updated successfully.
```

# Backup

Резервная копия создается одной командой:

```bash
./backup.sh
```

Пример результата:

```text
backups/
└── microshop-2026-10-08-004512.tar.gz
```

Backup должен включать не только PostgreSQL.

Минимальный состав:

```text
database.dump
uploads/
config.env
metadata.json
```

Таким образом сохраняются:

- данные БД;
- фотографии товаров;
- пользовательские файлы;
- конфигурация и постоянные secrets;
- информация о версии продукта и формате backup.

Для согласованности БД и файлов backend останавливается после завершения текущих операций, а PostgreSQL остается запущенным. Затем создается логический dump БД и копируются uploads и конфигурация. Один `pg_dump` не обеспечивает согласованность отдельно копируемых файлов.

При самостоятельном запуске `backup.sh` возвращает backend в исходное рабочее состояние после успешного backup. Если backend уже остановлен для update или restore, скрипт не запускает его самостоятельно.

Metadata содержит версию Microshop, ссылки на образы, версию PostgreSQL, время создания и версию формата архива. Backup с secrets доступен только владельцу установки. Постоянные secrets сохраняются при восстановлении, чтобы не терять возможность проверять существующие ссылки на заказы и другие подписанные данные.

# Restore

Восстановление:

```bash
./restore.sh backups/microshop-2026-10-08-004512.tar.gz
```

До изменения текущих данных скрипт проверяет архив, его формат, совместимость версий и доступность соответствующего deployment-комплекта и образов. При необходимости используется версия Microshop из backup; архив старой версии не загружается произвольно в текущую схему БД.

Перед восстановлением система должна предупредить пользователя:

```text
This will replace the current Microshop data.

Current installation will be backed up first.

Continue? [y/N]
```

Перед restore автоматически создается backup текущего состояния.

Backend останавливается на время backup и восстановления. Восстанавливаются БД, uploads и конфигурация с постоянными secrets, затем запускается соответствующая версия продукта и выполняется healthcheck.

Если backup текущего состояния создать невозможно, скрипт по умолчанию останавливается и сообщает причину. Продолжение без него требует отдельного явного подтверждения пользователя; ошибка не игнорируется автоматически.

# Хранение пользовательских файлов

В первой версии не требуется S3 или MinIO.

Фотографии и другие пользовательские файлы хранятся локально в persistent Docker volume.

Концептуально:

```text
/var/lib/microshop/uploads
```

Работа с локальным хранилищем сосредоточена в одном компоненте backend. Реализация S3 и дополнительная инфраструктура не входят в первую версию.

Пользователь скачивает deployment-архив опубликованного релиза, распаковывает его и запускает installer:

```bash
mkdir microshop
tar -xzf microshop-deploy-1.4.0.tar.gz -C microshop
cd microshop
./install.sh
```

После подключения DNS:

```bash
./domain.sh shop.example.ru
```

После подключения HTTPS и настройки магазина через браузер пользователь получает готовые:

```text
магазин
админку
backend
базу данных
HTTPS
```

без необходимости понимать внутреннее устройство системы.

Microshop остается headless backend для разработчиков, но одновременно является полноценным готовым интернет-магазином для пользователей, которые не хотят самостоятельно разрабатывать и разворачивать frontend.
