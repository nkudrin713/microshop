# MS-01: задачи на основу backend

## Цель и статус

Результат этапа: backend запускается на пустой PostgreSQL, применяет миграции,
проверяет JPA-маппинг, предоставляет healthcheck и единый формат ошибок API.
Механизм audit сохраняет безопасные записи в транзакции вызывающей операции.
Ошибка миграции или проверки маппинга исключает готовность приложения.

Это план реализации. Статусы задач отражены в таблице ниже; завершение
MS-01-01 не означает готовности всего этапа. Каждая задача выполняется
в отдельном чате.

Источники требований:

- [ROADMAP.md](../ROADMAP.md) — границы MS-01 и порядок этапов.
- [DATA_MODEL.md](../DATA_MODEL.md) — общие соглашения, JPA, `admin_user`, `audit_log`.
- [DELIVERY.md](../DELIVERY.md) — конфигурация, миграции и healthcheck.
- [CONCEPT.md](../CONCEPT.md) — требования к audit и надежности.

## Предварительное условие

Полное подготовительное проектирование из ROADMAP.md пока не завершено.
Для MS-01-01 отдельно согласована основа каркаса в
[ARCHITECTURE.md](ARCHITECTURE.md): один Gradle-проект, пакет
`dev.nkudrin.microshop`, Spring MVC, выбранные JPA/Flyway и отдельные тесты.
Этого достаточно для реализации MS-01-01; решения для следующих задач
уточняются до их реализации.

Ниже определены границы задач и приемка. Имена пакетов, точные версии,
формат ошибок и другие еще не согласованные детали не считаются утвержденными
только из-за включения в этот список. При реализации они берутся из
`ARCHITECTURE.md`; расхождения согласуются до изменения кода.

## MS-01-01. Каркас и сборка

**Цель:** проект компилируется и имеет одну точку входа Spring Boot.

**Зависимость:** согласованная основа каркаса в `ARCHITECTURE.md`.

**Объем:**

- Создать один Gradle-проект backend с Kotlin и Gradle Wrapper.
- Зафиксировать совместимые стабильные версии JDK, Kotlin, Spring Boot и
  Gradle; зависимости из BOM Spring Boot не версионировать независимо.
- Подключить необходимые для этапа механизмы MVC/JSON, валидации, JPA,
  Flyway, PostgreSQL, Actuator и тестирования. Учесть Kotlin-плагины для
  Spring и JPA; точный состав определяется выбранными версиями.
- Создать точку входа и структуру пакетов по `ARCHITECTURE.md`.
- Добавить исключения для результатов сборки, локальной конфигурации и secrets.

**Приемка:**

- Gradle Wrapper использует фиксированную версию; исходники компилируются
  выбранным JDK.
- Нет отдельных сервисов или Gradle-модулей для каждого домена, пустых CRUD
  и фиктивных торговых классов.
- Команды сборки и требования к локальной среде описаны в `docs/MS-01/DEVELOPMENT.md`.

Запуск с БД проверяется в MS-01-03. Авторизация и Spring Session реализуются
в MS-02; добавлять их поведение в каркас не требуется.

## MS-01-02. Тестовое окружение PostgreSQL

**Цель:** интеграционные тесты получают отдельную настоящую PostgreSQL.

**Зависимость:** MS-01-01.

**Объем:**

- Настроить JUnit, Spring Test и Testcontainers PostgreSQL.
- Зафиксировать версию образа PostgreSQL, совместимую с целевой поставкой;
  не использовать `latest`.
- Связать время жизни контейнера с тестовым контекстом Spring и передавать
  параметры подключения через готовую интеграцию Spring Boot.
- Обеспечить изоляцию данных между тестами. Тесты commit и конкурентных
  операций не должны зависеть от автоматического rollback тестового метода.

**Приемка:**

- Узкий тест подключается к контейнерной PostgreSQL и выполняет SQL.
- Повторный запуск не использует данные предыдущего запуска.
- Тестовая конфигурация не подключается к пользовательской или production-БД.
- Если Docker недоступен, причина видна; обязательные интеграционные тесты
  не пропускаются молча и не подменяются H2.
- В `docs/MS-01/DEVELOPMENT.md` описаны требования и команды запуска тестов.

## MS-01-03. Конфигурация БД, Flyway и JPA

**Цель:** приложение запускается на пустой БД и управляет схемой только через
миграции.

**Зависимость:** MS-01-02.

**Объем:**

- Настроить подключение к PostgreSQL через внешнюю конфигурацию без secrets
  в исходниках. Описать необходимые параметры в `docs/MS-01/DEVELOPMENT.md`.
- Настроить Flyway при старте, `ddl-auto=validate` и отключить Open
  EntityManager in View.
- Первой миграцией создать `admin_user` по DATA_MODEL.md: эта таблица нужна
  для FK из `audit_log` в MS-01-05. Не создавать владельца и не реализовывать
  вход, setup или административный API.
- Определить порядок версионирования миграций; уже примененные миграции
  не изменять ради обновления существующей БД.

**Приемка:**

- На пустой PostgreSQL приложение применяет миграции и запускается.
- Повторный запуск не пересоздает таблицы и сохраняет существующие данные.
- Проверены ограничения `admin_user`, включая уникальность логина.
- Ошибка SQL-миграции в отдельном тестовом сценарии прерывает запуск;
  ошибочная миграция не включается в основной набор.
- Эффективная конфигурация JPA не включает генерацию схемы и Open
  EntityManager in View. Поведенческая проверка несовпадения маппинга
  выполняется после появления сущности audit в MS-01-07.

## MS-01-04. Общие ошибки и валидация API

**Цель:** некорректный запрос получает предсказуемый JSON-ответ по общему
контракту API.

**Зависимость:** MS-01-01 и API-соглашения из `ARCHITECTURE.md`.

**Объем:**

- Реализовать общий обработчик ошибок и Bean Validation входных DTO.
  Рекомендуемая основа — Spring `ProblemDetail` и `@RestControllerAdvice`;
  окончательный формат определяется подготовительным проектированием.
- Обработать ошибки JSON, типов параметров, полей DTO, неподдерживаемого
  метода и формата содержимого, а также неожиданные внутренние ошибки.
- Предусмотреть преобразование ошибок операций в согласованные коды и
  HTTP-статусы без реализации самих торговых операций.
- Исключить из ответов внутренние исключения, SQL, stack trace и secrets;
  не журналировать целиком тело запроса, cookie и заголовки авторизации.

**Приемка:**

- MockMvc проверяет некорректный JSON, неправильный тип параметра, нарушение
  ограничения DTO, неподдерживаемый метод/формат и внутреннюю ошибку.
- Ответы соответствуют одному контракту; у ошибок полей есть привязка к полю.
- Контрольные чувствительные значения не попадают в ответы и журналы.
- Для этих проверок используются тестовые контроллеры; диагностические
  endpoint не добавляются в production-приложение.

Ответы 401/403 от фильтров Spring Security проверяются при интеграции доступа
в MS-02 по тому же контракту ошибок.

## MS-01-05. Транзакционный audit

**Цель:** вызывающая операция записывает audit атомарно со своим изменением.

**Зависимость:** MS-01-03.

**Объем:**

- Добавить миграцию `audit_log`, включая FK на уже созданную `admin_user`,
  ограничения и индексы из DATA_MODEL.md.
- Реализовать JPA-маппинг, репозиторий и механизм записи audit с явным
  автором `ADMIN` или `SYSTEM`, действием, объектом и безопасными снимками.
- Запись участвует в существующей транзакции; отдельная независимая
  транзакция и отправка записи после commit не используются.
- Снимки собираются из явно разрешенных данных. Автоматическая сериализация
  всей сущности или входного запроса не применяется.
- Не создавать API просмотра audit и не подменять им `order_event`.

**Приемка:**

- При commit сохраняются изменение и audit; при rollback не сохраняется ни
  одно из них. Ошибка записи audit не оставляет изменение без журнала.
- `ADMIN` требует существующего пользователя; `SYSTEM` допускает отсутствие
  пользователя по DATA_MODEL.md. Неверные данные отклоняются ограничениями.
- Проверены чтение и запись JSON-снимков и времени через JPA на PostgreSQL.
- В снимки не попадают пароли, token и secrets; проверка не ограничивается
  утверждением, что эти данные отсутствуют в тестовом запросе.
- Тесты используют подготовленные записи и тестовую операцию без API
  создания владельца и без торговой логики.

## MS-01-06. Healthcheck backend

**Цель:** `/actuator/health` показывает реальную готовность backend по DELIVERY.md.

**Зависимость:** MS-01-03.

**Объем:**

- Настроить готовый Actuator healthcheck с проверкой доступности PostgreSQL.
- Успех возможен только после успешного старта с миграциями и проверкой JPA.
- Не связывать готовность инфраструктуры с завершением setup, публикацией
  магазина или включением продаж.
- Ограничить доступные HTTP-endpoint Actuator необходимой проверкой здоровья;
  публичный ответ не раскрывает конфигурацию и детали инфраструктуры.

**Приемка:**

- После успешного запуска на тестовой БД endpoint возвращает HTTP 200 и `UP`.
- При потере соединения с БД проверка возвращает неуспешный статус.
- Ошибка миграции не позволяет получить успешный healthcheck нового запуска.
- Отсутствие созданного владельца не делает работающую инфраструктуру
  неготовой; `/actuator/env` и другие служебные endpoint не открыты.

Проверки Caddy, storefront, installer и Docker healthcheck относятся к MS-13.

## MS-01-07. Приемка основы приложения

**Цель:** подтвердить совместную работу основы и подготовить передачу в MS-02.

**Зависимости:** MS-01-04, MS-01-05, MS-01-06.

**Объем и приемка:**

- Проверить итоговые diff и выполнить полную проверку реализованного backend.
  Ранее успешные узкие тесты повторяются только в составе итоговой проверки.
- На чистой PostgreSQL применяются все миграции, Hibernate проверяет audit,
  backend запускается и healthcheck успешен без владельца.
- Повторный запуск сохраняет данные. Тест с несовместимой схемой подтверждает,
  что `ddl-auto=validate` прерывает запуск и не исправляет схему автоматически.
- Проверены негативные сценарии миграции, недоступной БД, ошибок API и
  rollback audit; неуспешная проверка не скрыта и не помечена пройденной.
- `docs/MS-01/DEVELOPMENT.md` содержит фактические команды сборки, тестов и локального
  запуска с отдельной PostgreSQL, а также названия обязательных параметров
  конфигурации без реальных secrets.
- При завершении задачи отмечены выполненные пункты этого документа и
  устранены расхождения реализации с согласованной архитектурой.

MS-02 использует готовую таблицу `admin_user` и audit; повторно создавать
таблицу отдельной несовместимой миграцией не требуется.

## Границы этапа

В MS-01 не входят setup, вход владельца, Spring Session/CSRF, настройки
магазина, каталог, корзина, checkout, торговые расчеты и переходы, шифрование
token заказа, отправка уведомлений, frontend, CI/CD и production-поставка.
Их технические условия учитываются в архитектуре, реализация остается в
соответствующих этапах ROADMAP.md.
